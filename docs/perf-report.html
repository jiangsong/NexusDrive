04

做了什么

readdirplus 由目录句柄填充

冷遍历 1,239 → 299 ms

go-fuse 对每个条目调 node.Lookup（两次 SELECT）；目录句柄实现 FileLookuper 后由列举本身回答，2041 项零逐条查询。目录句柄惰性列举、挂载 noatime 各省掉一次每目录的开销。

SFTP 句柄复用 + ReadAt 并发 + 255 KiB 包

冷随机 200 → 1,331 IOPS，拉取 110.9 → 9.6 MB；冷顺序读 125 → 279 MB/s（直连）

此前每个范围 OPEN + 串行 32 KiB READ + CLOSE。现在同一路径同一版本共用一个远端句柄，一次 ReadAt 由 pkg/sftp 并发拆包；改名/删除前先关句柄。

子块 16 KiB

一次未命中只拉内核要的 16 KiB

READ 尺寸直方图：≤4 KiB: 1, ≤16 KiB: 498, ≤64 KiB: 498, ≤128 KiB: 498, ≤1024 KiB: 498。

SQL 精简

负缓存进内存、Path 单查询、create/flush 少 4 次点查

每个操作的 SQL 预算写进 test/perf。

durability: crash（可选）

500 小文件 262（power）/ 685（crash）个/s

power 是默认：close() 等三次 fsync；crash 一次都不做，进程崩溃不丢，掉电可能丢最后几秒并报为死信。

第五轮：矩阵跑挂逼出来的正确性缺陷

四档矩阵 + fio 全绿，队列零死信

矩阵在换数据集大小时读到一个 0 字节的文件，追下去是一串写路径缺陷：重写一个变小的文件会保留旧尾巴（内核先 open 再用另一个句柄 truncate，而 open 当场就把旧内容下载进了 staging）；重写会被判成自己和自己冲突（第二次上传对着第一次上传之前的版本比较）；同一文件的两次上传彼此赛跑；本地已删除的文件上传失败后进死信。修法分别是：staging 第一次写才建、被取代的上传只取远端版本、按 inode 取代加上传侧让路、文件已不在就丢弃。顺带：截断到 0 不再先下载整份内容，重写只排一次上传。

第四轮：后台工作让路，尺子再加一格

冷随机读 1,310 → 1,768 IOPS（矩阵顺序的直连探针）

CPU profile 指认了两处不在读路径代码里的开销：随机读期间 35% 的 CPU 花在目录预取的元数据写入上；hydrate 又会在读完 256 MiB 后立刻把整份文件再拷一遍，正好压在下一波读上。现在预取与 hydrate 开始前都先问「前台有没有读在等」，hydrate 每拷一个块再问一次，空闲判据从 2 s 放宽到 10 s。partial 块的 claim 改为「先写空 claim 再写数据」——此前先数据后 claim，中间崩溃会让重载把没取过的字节当命中。

第三轮：把每个门禁拉过线

详见下方门禁表

写路径：FLUSH 后惰性重建 staging、父目录路径/id 按 ino 缓存、写事务预编译、内核自己发起的变更不再向内核发失效。读路径：整块 write-behind（内存先服务、后台落盘）、hydrate 推迟到空闲、驱动直接填缓冲（发现包装层曾把这条路藏掉）、块缓冲池化、预读对在飞的块只留一个等待者、partial 块 fd 常驻、子块也 write-behind（整块给子块留 32 MiB 内存）、sidecar 只记已落盘的子块、≤256 KiB 读固定走第一条 SSH 会话、SSH 会话池。元数据：未变化的目录刷新只刷 fetched_at。

06

这一轮修掉的缺陷

都是在真实链路上被数字逼出来的：要么是干净矩阵的某一列不对劲，要么是加固测试挂了。每一处都有回退即失败的测试。

F-01

建文件是 O(N) 的

lookup 未命中时为了确认列举新鲜把整个目录读进内存；一个目录建 2000 个空文件花 39 s，每个 20 ms 且随 N 增长。改为只确认新鲜、不加载。

internal/vfs/vfs.go freshenDir · TestCreatesDoNotRescanTheDirectory

F-02

随机读误触发预读

块相邻就算顺序读，256 MiB 上 500 次随机读碰巧相邻 ~15 次，每次拉两个整块，116 MB 里 89 MB 是这么来的。改为连续 3 次读起点接续、且距离按块大小取。

internal/vfs/read.go seqArm/seqSlack · TestRandomReadsDoNotArmReadAhead

F-03

旁边跑一次 cloudfs status，close() 就报 EIO

两个 SQLite 库的写事务都是 deferred BEGIN，另一进程在 SELECT 和 UPDATE 之间提交就得到不可重试的 SQLITE_BUSY_SNAPSHOT。改为 _txlock=immediate。

internal/meta, internal/journal · TestWritesWaitForAnotherProcessInsteadOfFailing

F-04

提交中途失败后句柄报废

staging 改名到对象目录之后再出错，下一次 FLUSH 又去 fsync 已关闭的文件，数据困在对象目录里。提交步骤记在句柄上，重试从断点续做。

internal/vfs/write.go pendingCommit · TestFlushResumesACommitThatFailedHalfway

F-05

首次列举把内核正在填充的目录缓存扔掉

每次拉取目录后都向内核发失效，而内核恰好在用这次 readdirplus 填它的目录缓存；于是每次热遍历都重读冷遍历拉过的目录。改为只在「已缓存的目录真的变了」时按条目失效。

internal/vfs/vfs.go invalidateListing · TestListingInvalidatesOnlyWhatChanged

F-06

服务端截短的 READ 被当成完整块入缓存

pkg/sftp 把短块报成 EOF，VFS 接受 EOF 并把短块当完整块缓存——之后这个文件读出来就是被悄悄截断的。驱动追读剩余部分，VFS 拒绝短块入缓存。

internal/vfs/read.go shortRead · TestShortReadIsNeverCached, TestReadRangeFollowsUpAShortAnswer

F-07

恢复只检查 blob 存在，不核对内容

掉电截断的 blob 会被当成完整文件上传。现在核对 size，crash 模式再核 crc32c；不符的进死信并写明原因。

internal/journal/journal.go verifyBlob · TestRecoverDeadLettersBlobsThatDoNotMatchTheirRow

F-08

死信后的节点仍指向已丢失的本地数据

读它永远 EIO 或读到撕裂字节。RepairLost 摘掉节点、作废父目录列举，下一次读回远端版本。

internal/vfs/write.go RepairLost · TestLostUploadIsRepairedInTheTree

F-10

删除与认领的竞争让文件复活

unlink 在看队列与丢行之间，uploader 刚好认领了这一行；丢掉它，上传照样完成，下次列举文件复活。DropPending 只删仍在 pending 的行，已认领的打墓碑。

internal/journal/journal.go DropPending · TestDropPendingLeavesAClaimedRowForTheTombstone

F-11

改名后提交在旧名字下插入第二个节点

提交与上传完成都按（父目录，名字）Upsert；中间改过名就多出一个旧名节点，而新名节点的本地数据随即被释放，读它永远 EIO。改为按 inode 更新；打开后被 unlink 的文件 close 时不再复活。

internal/meta/store.go UpdateByIno · TestCommitAfterRenameKeepsTheNewName, TestWriteAfterUnlinkDoesNotResurrectTheFile

F-12

上传落地后旧的读句柄读不到文件

落地释放了 local-only 缓存项，之前打开的句柄还带着旧身份。读路径在本地 key 消失时重新取节点身份。

internal/vfs/read.go · TestReadHandleSurvivesUploadCompletion

F-13

每次目录刷新都重写整个目录的 FTS 索引

PutDir 把所有子项重新排队，indexer 逐项做一次全表扫描的删除再插入；强制刷新的压力测试在 race 检测下跑不完。改为只排队索引里没有或改了名的项，FTS 行按 rowid 定位。

internal/meta/store.go, indexer.go · TestRefreshQueuesOnlyChangedNamesForTheIndex

F-14

免费空间检查的节流记住了失败

缓存满时第一次检查失败后，一秒内的后续写入跳过检查照常入缓存。失败的检查不再计入节流。

internal/cache/blockcache.go makeRoom · TestFullDiskIsCheckedAgainOnEveryWrite

F-15

partial 块先落数据、后写 claim

重载把「有块文件、没有 sidecar」读作整块。此前 flush 先写数据再写 claim，中间崩溃就会让下次启动把从没取过的字节当成命中返回。改为建块文件前先写一份空 claim，之后的 claim 只会少认、不会多认。

internal/cache/subblock.go claimBlock · TestPartialBlockFileNeverExistsWithoutItsClaim, TestClaimsCatchUpAfterTheWritesStop

F-18

重写一个变小的文件会保留旧尾巴

内核不把 O_TRUNC 随 open 发过来：先 open，再用另一个句柄 truncate。而 open 当场就把整份旧内容下载进 staging，于是 truncate 作用在另一份 staging 上，新写的字节落进那份满尺寸的文件，提交时把旧尾巴一起传回后端——本地和远端都错，而且无声。staging 改为第一次写才建。

internal/vfs/write.go openStaging · TestRewritingAFileSmallerDoesNotKeepTheOldTail, TestTruncateThroughAnotherHandleIsNotUndone

F-19

重写被判成自己和自己冲突

重写是两次上传：truncate 一次、内容一次。第二次声明「我从哪个远端版本开始改」，而第一次（我们自己的）已经把版本推进了，于是内容被写进 conflict 副本，原文件停在 0 字节。被取代的上传完成只取远端版本，不取尺寸和 id。

internal/vfs/write.go UploadHooks · TestRewritingAFileDoesNotLandAsAConflictCopy

F-20

同一文件的两次上传彼此赛跑

两次上传写同一个远端路径，工作线程并行跑，先排队的小的那次可能后落地。现在上传前先看有没有更新的提交（有就跳过），再看有没有更早的同文件上传还在飞（有就让路，不计重试次数）。

缓存重启后认不出自己的文件

保留意见

  • unlink 仍是 ~160/s。限流放开后瓶颈换成了 journal：删除一个还在上传队列里的文件要给它打墓碑（一次 FULL 同步的事务）， 而 uploader 同时在为每个上传写三次同步事务。它没有门禁；异步删除队列记在 TODO。
  • 热遍历剩下的 41 次 getattr是内核在 readdir 后对目录属性的一次重取，每目录一次；0.25 ms 一次，不影响门禁，但不是零。
  • power 模式小文件到不了 400/s。单线程 close() 串行付 fsync 是设计选择；要那个数字就选 crash 模式，报告两者都给。
  • 冷随机读的门禁取决于后端当时有多少 CPU。新的 cloudfs_remote_seconds_total 把每次读拆成两半：我们自己的代码稳定在 ~150 µs，SFTP 调用内部则在 446–980 µs 之间摆动。1,500 IOPS 相当于每次 667 µs，所以后端 每次调用低于 ~515 µs 时达标（实测 1,534–1,974），高于 600 µs 时不达标（实测 1,265–1,331）。 测量期间后端主机（4 核）上有一个与本项目无关的 snap-store 常驻占用 2.6 个核， 已经跑了 104 天；没有去动别人机器上的进程。
  • 本轮的数字对测量顺序敏感。随机读紧跟在 256 MiB 顺序读之后，磁盘还在消化上一项； 让后台工作（目录预取、hydrate）给前台读让路之后差距从 ~40% 收敛到噪声范围，但表里仍同时给出最好一次（min）。
  • 后端主机也是共享的。192.168.0.20 是 4 核，测量期间有一个与本项目无关的 snap-store 进程常驻占用 2.6 个核（已运行 104 天），sshd 与 sftp-server 和它抢 CPU。 直连冷顺序读的中位数因此在 130–320 MB/s 之间摆动，而新的每操作耗时显示这段时间确实花在 SFTP 调用内部，不在调用之上的代码里。没有去动别人机器上的进程。
  • 本机负载。测量期间 4 核机器的 load average 在 9–10（另一个会话与一个 D 状态的残留测试进程）， 所有数字都是在这个条件下取的；表里同时给出最好一次（min）。
  • 经代理的数字比直连低：netem 是用户态 Go 代理，每个字节多过两次内核；lan 档保留是为了与 wan/bad 同基线。
