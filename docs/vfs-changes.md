# VFS 变更事件流

`FS.WatchChanges()` 提供独立于 FUSE 缓存失效的进程内事件流，供 MCP 订阅等适配层使用。
当前已接入 VFS 与 MCP 新旧资源订阅协议；协议限制与测试边界见 [MCP 接口](mcp.md)。

> **`vfs.Change` 不是审计日志。** 它是内存里的、有损的、不带主体的"该重新读了"提示：
> 不区分是内核、agent 还是远端刷新引起的，不落盘，进程重启即空，也不承诺每次变更都送达。
> 持久的"谁、什么时候、用哪个工具、对哪些路径做了什么（含被拒绝的调用）"记录在
> `<cache.dir>/agent/agent.db` 的审计表里，见 [MCP 接口](mcp.md) 的"审计"一节
> （`cloudfs audit`、`GET /audit`、控制台「Agent」屏）。两者互不替代：审计只覆盖 MCP
> 工具调用，不覆盖内核写；变更提示覆盖全部来源，但没有主体与结果。

## 语义与生命周期

- 返回只读 channel 与幂等取消函数。消费者必须取消；`FS.Close` 会关闭剩余订阅，关闭
  后不能重新订阅。取消/关闭后 channel 中可能还有此前排队的提示，适配层需先移除其
  客户端订阅关系，再停止处理，不把旧提示发给已取消的客户端。
- `Change.Paths` 是虚拟路径，不含 provider ID、凭据或缓存文件名。`Subtree` 表示后代
  路径也可能失效，例如目录改名/删除；`Rescan` 表示无法精确给出路径，需要重新检查
  订阅资源。`Affects` 匹配路径本身、直接父目录的列表，以及受影响子树中的后代。
- 这是“重新读取资源”的提示，不是持久审计日志，不承诺逐版本或恰好一次交付。多个
  操作、完整本地发布后的重试、远端刷新可产生重叠提示；消费者应按订阅 URI 合并，
  必要时重新读取。进程重启后客户端需重建订阅并重新读取，不能续接旧事件序号。
- 每个消费者最多排队 64 条，每条超过 128 个路径会退化为重查。队列满时清空待消费
  提示并放入 Rescan，不无声丢弃一致性信息。发送不会等待消费者，不调用消费者回调，
  不创建每事件 goroutine；各消费者获得独立路径切片。MCP 应每个服务使用一个事件流，
  而不是每个资源创建一个 VFS 消费者，并另外限制客户端订阅数。
- 未订阅时不会为通知查询元数据路径。有订阅时路径来自本地元数据，不访问 provider；
  路径解析失败用 Rescan 提示，不能因此改变已完成文件操作的返回结果。

## 已接线的变更

- 新建文件、已发布的本地写入、建目录、删除和改名。内核来源写入同样发送，但仍不
  对内核自身发起的操作发送 FUSE 失效，保留原有性能约束。改名的新旧路径在同一条
  提示中发送，目录后代也可失效。
- 本地复制完整内容绑定后立即通知，不以上传交接成功为前提；服务端复制在本地节点
  插入成功后通知。发布恢复、上传落地，以及使父目录变旧的上传特殊路径也已接入。
- 远端 delta 更新/删除，及未知子项令已知父目录变旧的情况。目录 TTL/显式刷新使用
  实际 `DirChange` 的新增、删除和更新，删除后仍保留旧虚拟名称；未变化的刷新安静。
- 恢复修复丢失的本地版本时，发送原名称的失效提示。

## 验证与剩余边界

已有测试覆盖内核来源写入而不发生内核自失效、目录改名/删除后代、delta 更新/删除、
重复 delta 与未变化刷新、列表新增/删除、慢消费者溢出、消费者数据隔离、并发取消与
关闭，以及复制交接失败但完整本地版本已经可读的通知时机。

MCP 已接入注册/取消/断连清理、通知合并和权限检查，只通知已授权的订阅 URI，不把原始
事件直接广播给客户端。每个 MCP 服务只使用一个事件流，协议层另有资源/会话/流数量上限。
大量订阅和真实 FUSE/网盘长期运行尚未验收；直接绕过 VFS 改元数据库不在此事件流承诺中。

## `changes` 表：内存事件 vs 持久事实（T-51，2026-09-16）

`vfs.Change` 是内存事件：64 条缓冲，溢出坍缩成一条 `KindRescan`，进程退出即消失。`internal/agent` 的 `ChangeRecorder`
（daemon 装配的第五个 `WatchChanges` 消费者，200 ms / 128 条攒批，只在 owner 进程跑）把它落进 agent.db 的 `changes` 表：
`(id, ts, path, kind, from, origin, session_id?, principal?, reliable)`。`origin` 来自 `WithOrigin` 打的标（`kernel` / `mcp` /
`control` / `webdav`），`session_id` / `principal` 来自 mcpsrv session middleware 的 `WithActor`。收到 `KindRescan` 时记一行 `kind = rescan`、
`reliable = 0`——含义是"这行之前可能有遗漏"，之后的行照常 `reliable = 1`；`pull_events` 与 hooks 注入都据此提示
"可能有遗漏"。记录器启动时若表里已有行，也记一条 `origin = restart` 的 rescan 行：守护进程停着（或 kill -9 时攒批
未落）的那段没人记录，用同一个标记诚实地说出来（2026-09-17）。
`stat.last_writer`、`history`、`pull_events`、hooks 的"自上一轮谁改了什么"、控制台的变更标签都只读这张表；`mcp.session.retain`
（默认 30 天）到期后由 `RunChangeRetention` 清理。
