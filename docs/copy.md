# 文件复制：当前实现与验收边界

## 使用

```sh
cloudfs cp /work/source.bin /archive/dest.bin --timeout 30m
cloudfs cp /work/source.bin /archive/dest.bin --json
cloudfs copies list --limit 200 --json
cloudfs copies show <copy-id> --json
cloudfs copies cancel <copy-id>
cloudfs copies retry <copy-id> --timeout 30m
cloudfs copies forget <copy-id> --confirm
```

路径是配置 layout 中的绝对虚拟路径，不是操作系统挂载点路径。目标必须是明确的
文件名，父目录必须存在。当前是单文件原语：不递归复制目录，也不提供覆盖模式。
MCP `copy` 使用 `from`、`to`，两端都受允许列表约束，只读服务拒绝执行。

CLI 优先调用现有 daemon 的控制接口；只有尚未发出请求且端点明确不可连接时才离线
打开存储。离线必须取得 journal 所有权，不启动上传、预取或刷新后台任务。
离线 writeback 成功后可启动 daemon 或执行 `cloudfs uploads flush` 完成排队上传。
已连接后的超时、响应丢失或服务器错误不会触发离线重放。

## 数据路径与成功含义

- 同一 remote、源为干净远端文件、目标驱动声明服务端复制能力时，使用服务端复制。
  只有明确的 `ErrUnsupported` 才回退；超时等结果不确定的错误不能安全重试。
- 其他情况先准备源的完整内容，再创建目标。已有完整缓存时尝试复用不可变 inode，
  按目标的哈希要求计算摘要；无法硬链接时流式复制，缓冲区上限 1 MiB。
- 源使用已提交内容，不会隐式 flush 仍打开的写句柄。尚无提交版本的新文件返回忙。
- writeback 成功表示内容已提交到本地上传日志；strict 成功要等待远端完成。
  目标支持秒传且已具有相同内容时，上传器可以只发送哈希握手，不发送分片。
- 上传日志带持久化 `needs_publish` 标记，缓存与目标元数据发布完成前不能被上传器
  领取。power 模式的元数据发布事务单独使用 FULL 同步；daemon 启动在刷新/上传前
  补完中断发布。已确认待传版本的缓存链接丢失时，可从 journal blob 重建。
  恢复时若目标 inode 缺失，不能区分删除与元数据损坏，因此保留为死信待对账，既不
  自动重建目标，也不据此删除唯一的持久化内容。
- 准备日志同时绑定原元数据库及源/目标挂载前缀、根对象和本地账号代次。未完成下载
  在 provider IO 前核对源，重试/发布核对目标；换绑或旧空绑定作业保留内容并拒绝
  自动处理。已交接上传再由 journal v11 的目标绑定二次围栏。
- 已存在的本地目标被拒绝，并发流式复制用原子元数据插入保证只有一个创建者获胜。
  源下载或空间准入失败发生在目标创建前，不发布部分下载内容。

缓存链接在操作前检查源路径为普通文件，操作后核对 inode 和大小。链接 staging
禁止 WriteAt/Truncate；同 inode 重命名为现有内容对象时显式清理私有 staging 别名，
不删除内容对象。完整缓存大小与已提交元数据不符时拒绝复制。

## 尚未完成

- **全程可恢复复制任务**：已提交 journal 的上传可在重启后恢复。准备阶段的作业、
  检查点校验和原子上传交接已接入 VFS Copy 及 daemon 后台恢复；VFS 子进程下载
  中途强杀后只补剩余字节的测试已通过。生产二进制 `cp` 强杀后由另一个生产
  MCP-only daemon 进程续跑的 HTTP WebDAV 验收也已通过。仍缺真实账号验收、
  已交接上传取消后的自动对账／版本清理和完整终态历史，不能认为 T-04 已完成。显式风险确认后的新上传尝试已有，见下文。已支持显式清理无引用的
  准备内容与作业记录，见下文及 [复制准备日志](copy-preparation.md)。
- **远端结果对账**：服务端已复制、但响应丢失或本地元数据插入失败时，仍缺持久化
  意图和统一对账流程。错误不能证明远端没有动作，应核对目标后再重试。
- **跨端创建竞争**：本地存在性检查与远端复制不是同一事务。其他客户端或服务端
  复制并发创建同名目标时，缺少跨驱动的原子“不覆盖”契约，不能声称全局无覆盖。
- **发布失败恢复的剩余窗口**：日志提交后的本地映射恢复已有实现及子进程强杀回归，
  目标节点与复制 ID 也已原子绑定，创建节点后、提交上传前强杀可复用原 inode。
  此阶段写打开/改名返回忙，删除会取消准备作业；准备目标改名语义仍需补齐，失败准备作业管理已有。
  服务端复制不经过这个上传发布标记，其结果不确定时的对账仍是独立待办。
- **真实网盘验收**：现有测试使用 fake provider、HTTP 控制面、真实 MCP 内存传输及
  本地持久化；生产 CLI 进程测试使用 HTTP WebDAV 模拟服务，不替代实际账号的
  服务端复制、秒传和故障恢复验证。

## 查询准备作业

`copies list` 默认返回 200 条、最多 1000 条，使用 `next_cursor` / `--cursor` 翻页；
`copies show <id>` 查询单条。CLI 优先连接 daemon 的 `GET /copies`，连接明确不存在时
只读打开日志，不初始化 provider、不启动恢复、不截断正在下载的未确认尾部。
旧版尚无准备表的日志返回空列表，不触发迁移；查询不存在的单条 ID 返回错误。

输出包含虚拟源/目标路径、状态、源长度和已确认检查点，不包含内部对象 ID/版本、
元数据库身份、payload 路径、哈希或原始持久化错误。failed 会给出内容保留的通用提示。
列表包含所有状态，按稳定 ID 分页；扫描期间新建且 ID 在游标之前的作业需下一轮查看。

`submitted` **只表示已交接上传，不代表远端成功**。此时 `upload_id` 指向上传任务，
继续通过 `uploads list` 检查 pending/uploading/dead/cancelling/cancelled；已被清理的上传行不应据此推断
成功或失败。当前没有完整的复制终态历史；MCP 已有受双路径权限限制的
`list_copy_jobs/get_copy_job`，以及 `retry_copy_job/cancel_copy_job/forget_copy_job`，
使用与分页边界见 [MCP 接口](mcp.md)。无引用的作业
可显式 `forget`，不能用清理结果推断此前上传是否成功。
不要直接删除准备 payload 或改写数据库状态来强制恢复。

未完成下载的恢复会重新按记录的源路径核对对象身份，而不盲目追踪稳定的后端 ID。
源改名、源账号换代或被新的挂载遮蔽时保留检查点并拒绝下载；这遵循 VFS 的缓存
一致性，不承诺跨客户端原子快照。已经准备完整的内容仍可在源被删除后交接，
不再次读取源；目标账号绑定仍必须匹配。

## 重试与取消

`copies cancel <id>` 持久化 cancelled 状态，并中断当前 daemon 中该准备任务的下载。
取消不是删除：检查点和 payload 保留，已创建的完整本地版本仍可读；写打开/改名仍
返回忙，直到显式重试交接或删除该本地目标。缓存链接丢失时，启动会校验完整 payload
并恢复链接及防淘汰保护，不会重新执行已取消的复制。校验会读取保留内容，大文件
启动开销尚待性能测量。

取消与上传交接竞争时只有一个能成功。若作业已 submitted，取消返回冲突，不假报
远端上传已停止，需要检查上传任务与目标现状。`copies` 不负责取消已交接的上传。
已交接的上传可使用 `uploads cancel <upload_id>`，返回停止中／已停止状态并保留本地
内容，不保证远端没有生效；普通 retry/drop 不会重新启动或销毁取消记录。已新增
`uploads resume <id> --confirm`：核对绑定与保留内容后发起新尝试，不复用不确定的旧
上传会话；接受远端可能重复／覆盖的风险，不等于自动对账。版本清理和完整历史管理
闭环仍待补。准备任务和上传任务的取消不是同一状态机。
取消成功后，已经开始的底层 IO 可能仍需退出，但不能再推进检查点或交接上传。

`copies retry <id>` 只接受 failed/cancelled，校验保留前缀后重新排队。重试保持原源对象、
版本、两端账号代次及目标身份；目标已删除、改名、换绑或同名占用时拒绝，未完成
下载的源换绑也在排队前拒绝，执行时仍再次验证源版本和挂载。
重试不会覆盖新的取消请求，也不会重新排队 active/submitted 作业。成功只表示排队，
不表示复制或上传完成；在线会唤醒恢复 worker。

两个命令优先调用原 daemon，已连接后的超时/响应丢失不触发离线重放。离线取消只需
取得 journal 所有权，不初始化 provider；离线重试构建带身份检查的 VFS、执行启动
恢复，但不启动后台下载/刷新/上传，新排队任务由之后启动的 daemon 继续。
重试默认超时 30 分钟，可用 `--timeout` 调整。
MCP-only owner 同样启动控制端点，因此没有 FUSE 挂载时也可在线管理准备任务。

`uploads list --json` 中 `needs_publish: true` 表示正在等待本地发布；文本列表也会标注。
短暂出现是正常提交过程。若命令已失败且长期保持该状态，应先排查缓存/元数据错误，
再受控重启 daemon 触发本地发布恢复，不应绕过标记强行上传或删除数据。
当前日志为 schema v11（v11 为已交接上传增加原元数据库、目标挂载与账号绑定；
v10 增加上传清理意图与丢弃后 ID 防复活凭据，VFS、启动续清理及在线/离线确认入口已接入，见 [上传清理边界](upload-cleanup.md)；v9 增加上传取消修订号和恢复前会话历史；v8 增加持久上传取消状态；v4 引入发布门禁，v5 增加准备日志，v6 增加准备取消状态和重试修订号，
v7 增加持久化清理意图）；新版本支持只读查看旧 v3/v4/v5/v6 日志且不迁移，
写打开取得所有权后才迁移。
不能在旧 daemon 持有日志时由新进程升级表。旧构建不能继续打开升级后的日志，
应保留升级前备份并避免混用二进制。

元数据库为 schema v9，v6 增加独立身份与持久化复制绑定，v7 增加清理前的 FULL 同步屏障，
v8 增加短字符串名称索引，v9 增加目录刷新代次。
后台恢复验证数据库身份、
挂载配置及源版本；不能验证时保留内容并报告警告，不按同名路径选择其他源/目标。
前台准备错误或请求超时产生 failed 作业，显式 `copies cancel` 产生 cancelled 作业，
二者都不自动续跑；强杀留下的 preparing/ready 作业可由正常启动的 daemon 接手。
离线复制成功仍只表示本地交接，只读管理不启动恢复。

目录递归、覆盖策略不是当前单文件接口提供的行为，若扩展应与上述恢复和竞争语义一起设计。

## 显式清理准备内容与记录

`copies forget <id> --confirm` 是不可撤销的清理操作：删除该作业的记录、无引用的
私有 payload 和对应本地版本缓存名，**不删除虚拟目录中的文件或远端文件，也不取消
上传**。仅接受 failed/cancelled/submitted，活动 preparing/ready 需先取消并等待准备
句柄退出。命令不提供按年龄或批量清理。

- 若元数据库仍有文件引用这份本地内容，拒绝清理；需先自行决定是否删除该本地目标。
  任意状态的上传行引用作业 ID 或 payload 时也拒绝，不能用 forget 绕过上传管理。
- 清理必须在原元数据库中执行。确认无本地引用后，以真实 FULL 事务同步此前的删除，
  再把作业转为持久化 `purging`。复制绑定墓碑不删除，防止旧日志恢复时复活已删除目标。
- 清理缓存、删除私有 payload 和最终移除意图之间发生故障，`copies list/show` 仍显示
  purging；payload 已删但数据库提交失败也可重试。可再次执行同一命令，正常 daemon
  启动或扫描时也会继续先前已确认的清理。不能 retry 将 purging 恢复为下载。
- 清理不递归删除目录，不跟随 payload 符号链接删除其目标；意外目录或存储错误会停止
  清理。其他硬链接和已打开租约可能继续保留物理字节，不能承诺立即释放同等磁盘空间。
- CLI 优先使用在线 `POST /copies/forget`（JSON 必须有 `confirm:true`）；离线需要取得
  journal 所有权并构建 VFS 验证数据库身份，不启动后台传输。在线响应丢失不自动重放。
  成功返回 `forgotten` ID，后续 show/forget 返回不存在，不伪造上传成功状态。

已有缓存删除失败、引用拒绝、打开租约、SQL 回滚、清理中子进程强杀及 CLI/HTTP 回归；
这不替代物理掉电、真实账号和长期存储故障验收。
