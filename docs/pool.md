# 存储池(Storage Pool)

存储池把多个网盘融合成**一个**目录:系统决定文件放在哪个网盘、每个文件保存 N 份副本、任何一个网盘掉线不影响其它文件、坏掉一个网盘副本会自动在其它网盘重建;本地磁盘只是一块有上限的热缓存。目标是治「本地磁盘焦虑」——把所有网盘的总容量当成一块永远可以继续加大的盘来用。

和市面上「一个网盘挂一个路径」的产品不同,它是一层放在现有 remote 之上的**复合后端**(`type: pool`),对 vfs/缓存/日志/上传队列而言就是普通的一个 remote。

## 一分钟上手

```yaml
remotes:
  ali:  {type: aliyun}
  gd:   {type: gdrive}
  nas:  {type: webdav, url: 'https://nas/dav'}
  home: {type: pool, pool: home}      # 暴露存储池的 remote,只有这一个键

pools:
  home:
    members:
      - {remote: ali}
      - {remote: gd, root: /cloudfs}  # 池的目录树镜像在这个网盘的 /cloudfs 之下
      - {remote: nas, root: /pool, capacity: 2TiB}
    replicas: 3                       # 目标副本数(默认 3)
    min_replicas: 1                   # close() 返回前必须落地的份数(默认 1)

mounts:
  - path: /mnt/cloud
    layout:
      /:        {remote: home}        # 存储池挂在根
      /raw/gd:  {remote: gd, mode: readonly}   # 仍可直连某个成员看原始内容
```

界面里「存储池」一屏可以创建池、加成员、迁出、停用、立即修复、核对分歧;`cloudfs pool status|create|add|remove|drain|enable|disable|repair|scrub|divergences|join|rebuild` 是同一套能力的命令行。

## 它是怎么工作的

**镜像目录树。** 持有某文件副本的每个成员,都在自己的池根目录下按同样的路径、同样的文件名保存它——在网盘官方 App 里看到的就是真实文件。成员是命名空间的**共享真相**;本机的 `pool-<name>.db` 只是一份可以随时重建的**副本索引**(哪个成员持有哪个路径、成员上的目录 id、内容令牌)。

**读。** 列目录 = 对持有该目录的成员并行列举后按名字取并集;同名不同内容以 mtime 最新者为准,败者以 `name (conflict 2026-09-06 nas).ext` 的稳定名字露出,读路径永远不改成员上的任何东西。读文件从最健康、最快的副本读,失败自动切换到下一副本;成员不可达时用索引里的快照顶上,目录绝不因为一个网盘掉线而变空。

**写。** 上传流式直送一个主成员(现有的断点续传、进度、秒传都保留),目录树只在 `CompleteUpload` 时提交;其余 N-1 份由修复 worker 从本地暂存(hold,上传时对 blob 的一个硬链接,受 `hold_max_bytes`/`hold_max_age` 约束)复制过去,不用重新下载。`strict` 模式的含义是 `min_replicas` 份落地。

**改名 / 移动 / 删除。** 对所有持有该条目的成员扇出;一个成员成功即返回。不可达的成员得到一条 **op-log**,回来后按「目标状态」幂等重放:改名目的地已在 → 完成;删除的对象已不在 → 完成;**内容在此期间被改过 → 拒绝删除并记录分歧**(永不删陌生内容)。超过 `op_ttl` 的记录被丢弃,该成员改做一次全量核对。

**健康。** 每个成员由调用结果推出 `up → degraded → down → out`(以及操作员的 `disabled` / `draining`)。一次 5xx、传输失败、鉴权失败算「够不着」;404/429/冲突是「答了」。`down` 的成员每 `probe_interval` 才被试一次,`out`(down 超过 `out_after`,默认 10 分钟)的成员上的副本不再计数,扫描会把它持有的文件排进修复队列在其余成员重建。`/status` 对**所有** remote(不只是池成员)都报告这个状态,侧栏的圆点就是它。

**放置。** 候选成员 = 在服务中、能拼出这个名字(见下)、有空间的成员;已经持有该路径的优先(覆盖写落在原地),然后按剩余空间(权重加成)、声明顺序。同一成员永远不放两份。

**命名规则。** 每个网盘都有拒绝的名字(SMB 的 Windows 保留名、OneDrive 的禁字符、大部分网盘的大小写折叠)。驱动在 `Caps.Naming` 里声明,池放置前先检查;运行时被拒绝的名字也会被**学习**下来,下次不再往那个成员放同类名字。没有一个成员能放的名字会以「不支持」加原因拒绝。

**容量。** 能报告配额的网盘(gdrive、webdav RFC 4331、aliyun)按剩余空间参与放置;不能的用 `capacity:` 配置值减去池已放置的字节数;都没有则不按空间优先。`df` 看到的是池容量 = Σ成员容量 / replicas。

**核对(scrub)。** 定期重新列举一部分目录,把网盘上发生的事收进索引:在官方 App 里删掉一份 → 当作副本丢失补回(删除请通过池做);在官方 App 里改名 → 报告为分歧(带新名字),不猜;多余的副本只在哈希证明内容相同且超过 `trim_grace` 后从声明顺序最靠后的成员裁掉。

**迁出(drain)。** 成员标记为 draining 后不再放置新文件,它的副本不再计数,修复 worker 把文件复制到其它成员,复制安全后逐个删除;迁空后可以从配置移除。

## 多机使用(一期即支持)

同一批网盘可以被多台机器各自挂成存储池。成员是共享真相,每台机器有自己的索引与 op-log;一致性来自成员的变更 feed / 目录 TTL,与今天多台机器挂同一个网盘完全同构。**不做租约或锁。** 每个成员根下有一个 `.cloudfs-pool.json` 标记文件(池 id、设置与其版本号、成员名、写入者),`cloudfs pool join <某个成员>` 从任意一个成员读到它就能在新机器上建出同一个池——不带 `--confirm` 时只打印读到的是哪个池、有哪些成员,加上 `--confirm` 才写进配置。

一期明确接受的异常,都是最终一致的:

1. TTL 窗口内两台机器同时改同一文件 → 后到者成为冲突副本,两份内容都保留。
2. 在官方 App 里改名 = 池视角的删除 + 新建,只报告不猜;界面上「以网盘为准」或「忽略」。
3. 离线机器晚到的 op-log 重放按幂等规则兜底;超过 `op_ttl` 直接丢弃并全量核对。成员**可达但拒绝**某个改名/移动(目标名被占、命名规则不允许、配额)同样进 op-log 重试;重试次数用完就登记分歧、不再声称这个成员持有该文件(副本数因此少一份,由修复在别处补上),而它上面那份旧副本原样留着——池不会删自己说不清来历的东西。
4. 时钟偏斜:两个内容的 mtime 相差 ≤ 2 秒视为不可判定,记作分歧并按声明顺序取胜者。
5. 两台机器同时修复同一文件 → 内容相同即良性;裁剪只在哈希一致且过了 `trim_grace` 之后。
6. 某台机器改了池设置(replicas 等)→ 标记文件里版本号更大的一方被保留,另一方在状态页收到提示,由人决定。

## 出问题时先看什么

`cloudfs doctor` 会把池的状态逐条列出来:哪个成员 out(以及「排空后移除」的命令)、哪个成员有积压的树操作、有多少文件低于目标副本数(以及 `cloudfs pool repair`)、有没有文件一个可读副本都不剩、`replicas` 是否被可用成员数封顶、本地暂存是否超预算、有多少分歧等人决定,以及每个可达成员上的 `.cloudfs-pool.json` 是不是这个池的标记。

索引(`pool-<名字>.db`)只是缓存,丢了不影响数据:`cloudfs pool rebuild <池> --confirm` 从成员重新扫出来。会动数据的三个子命令(`drain`、`remove`、`rebuild`)都要显式 `--confirm`,和 `copies forget`、`uploads discard` 一个规矩。重建后队列里原有的上传照常完成,状态页会给一条提示。守护进程启动时还会对账一次本地暂存目录,把崩溃留下的孤儿文件和指向不存在文件的记录清掉。

## 设置

| 键 | 默认 | 含义 |
|---|---|---|
| `replicas` | 3 | 目标副本数;成员数不足时按可用成员数封顶并在状态里标 `target_capped` |
| `min_replicas` | 1 | `CompleteUpload` 返回前必须落地的份数(`strict` 模式等到这个数) |
| `out_after` | 10m | down 持续多久判定 out,触发再复制 |
| `probe_interval` | 30s | down 的成员多久被试一次 |
| `op_ttl` | 7d | op-log 保留多久,超过即丢弃并全量核对 |
| `trim_grace` | 1h | 多余副本至少存在多久才裁剪 |
| `hold_max_bytes` / `hold_max_age` | 8GiB / 24h | 本地暂存的预算 |
| `scrub_interval` / `scrub_sample` | 24h / 0.05 | 定期核对的频率与抽样比例 |
| 成员 `root` / `weight` / `capacity` / `adopt` | `/` / 1 / 未知 / true | 镜像根目录;放置权重;网盘不能报告时的容量;是否把成员上已有文件纳入命名空间 |

## 本地无法验证、需要真实账号的

各网盘真实的配额 API 与语义;单目录条目上限、路径长度、真实的大小写敏感性与保留字(有运行时学习兜底);修复流量在国内网盘上是否触发风控;官方 App 直接删改 `.cloudfs-pool.json` 或成员根目录后的表现;`journal.dir` 与 `cache.dir` 跨文件系统时硬链接失败的比例;真实双机收敛时间;超大文件补副本的耗时。
